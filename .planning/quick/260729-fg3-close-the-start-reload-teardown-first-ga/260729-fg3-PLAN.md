<objective>
Close the Start-reload teardown-first gap in the orchestrator by making a reload BUILD-then-COMMIT
instead of DESTROY-then-REBUILD.

`StartOrchestrationConsumer.cs:36-37` currently calls `TeardownAsync` (which does
`scheduler.UnscheduleAsync(wf.JobId)` **and** `store.Remove(workflowId)`) and only then
`HydrateAndScheduleAsync`. That destructive-first ordering produces two defects:

1. **Transient L1 hole.** Between `store.Remove` and hydration's `store.Upsert`
   (`WorkflowLifecycle.cs:117`) the workflow is ABSENT from L1 on that pod for the duration of
   `1 + N` Redis round-trips (the root `StringGetAsync` at `:41` plus one per step in the BFS at
   `:80`). Any `IStepResult` handled by that pod inside the window hits the L1 miss at
   `OrchestratorPrePipeline.cs:74`, is acked as "completed-unresolved", and increments
   `orchestrator_step_unresolved` — a silently lost continuation. `WorkflowFireJob.cs:57` misses the
   same way.
2. **Destructive partial failure.** If the build throws mid-BFS (Redis fault), teardown has ALREADY
   removed L1 and deleted the Quartz job. The workflow is now absent from L1 AND unscheduled on that
   pod with no rollback. Redelivery is the only path back (these consumers ACK on normal return, so a
   redelivery implies the first attempt threw); if Redis stays down, it stays broken.

`HydrateAndScheduleAsync` is ALREADY build-then-commit internally — every Redis read accumulates into
a local `steps` dictionary, then one `store.Upsert` (`:117`) followed by `ScheduleAsync` (`:118`). On
its own it never leaves L1 partial. **The hole is created entirely by the caller's teardown.**

Purpose: make a Start reload atomic from a reader's perspective (L1 swaps old->new, never absent) and
non-destructive under fault (a failed build touches nothing), while preserving the one genuinely
necessary half of teardown — the old-JobId unschedule.

Output: a `WorkflowLifecycle` split into a pure-read build half and a mutate-only commit half, a
one-line Start consumer, `TeardownAsync` deleted, and two new hermetic facts pinning both properties.
</objective>
