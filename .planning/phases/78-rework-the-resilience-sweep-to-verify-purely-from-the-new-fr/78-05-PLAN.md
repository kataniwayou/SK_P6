## ROOT-CAUSE TENSION — reproduce verbatim, do NOT gloss over (from 78-04-SUMMARY.md + the gap):

Phase 77 made execution-scope Tier-1 ids (incl. `StepId`) UNIFORM across framework send+consume logs via `IncludeScopes`, and (D3) had the send side MINT+STAMP+LOG its outbound `{MessageId}`, and (D2) had the keeper open the execution scope. Consequently EACH genuine hop now emits MULTIPLE `{executionId, stepId}`-scoped framework records that ALL match the structural query (`exists StepId` + `exists ExecutionId` + `has MessageId`, `must_not ReinjectOutcome`):
  - `"hop executed {MessageId} {Outcome}"`  (ProcessorPipeline.cs:218) — the processor CONSUME "did-run" record.
  - `"result sent {MessageId} {Outcome}"`   (OutputTail.cs:94)          — the processor result SEND record.
  - `"fan-out {MessageId} {NextStepId}"`     (OrchestratorPrePipeline.cs:170) — the orchestrator dispatch SEND record.
  - (`"terminal reached"` OrchestratorPrePipeline.cs:107 — no MessageId; and keeper `"REINJECT … {ReinjectOutcome}"` — excluded by the D-02 `must_not`.)

`BuildRunTraces` currently discriminates the processor "did-run" record by `hasMessageId` (AnalyzerE2ETests.cs:532). Pre-Phase-77 ONLY the consume record carried a MessageId, so that worked. Post-Phase-77 `result sent` and `fan-out` ALSO carry `attributes.MessageId`, so `stepIdsByInstance[key]` collects 3–4 records per hop → each stepId repeats 3–4× → `RunTrace.FromStepIds` sets `HasIllegitimateDuplicate` on every hop → `Duplicates == StartedRuns` on every run. (78-04 per-execution evidence: one no-fault execution had 30 StepId records over 10 distinct stepIds, each hop 3–4×.)

THE NAIVE FIX IS FORBIDDEN: "de-dup by (executionId, stepId) before counting" collapses everything to presence-only and BLINDS the genuine effect-once/duplicate detection — which is the ENTIRE POINT of the resilience proof (detecting a step that genuinely executed twice via redelivery/re-injection). The fix must distinguish "one genuine execution logged N times by framework send/consume records" from "the same step genuinely executed twice." The correct approach is to count a SPECIFIC canonical record kind that fires EXACTLY ONCE per genuine execution — the processor-side `"hop executed"` consume record — NOT to collapse all records. Two `"hop executed"` records for one `{executionId, stepId}` is a genuine redelivery and MUST still trip Duplicates.
