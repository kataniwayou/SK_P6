<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| orchestrator → processor entry queue | EntryStepDispatch arrives; payload already schema-validated upstream by Gate A/B (no new untrusted boundary added this plan) |
| processor/keeper → Redis L2 | Guid-typed keys (`skp:out:{messageId:D}`, `skp:data:{entryId:D}`) — no string interpolation of untrusted input |
| internal bus → keeper-recovery / post queues | same trust boundary as the entry queue (internal RabbitMQ) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-70-01 | Tampering | L2 key injection via OutputData/ExecutionData | accept | Keys are `{Guid:D}`-formatted (StackExchange.Redis Guid format) — no untrusted string is interpolated into a key; injection is structurally impossible. |
| T-70-02 | Information Disclosure | DataResult.Data carries raw-JSON output on the bus | accept | Internal bus, same trust boundary as the existing EntryStepDispatch.Payload; no new external surface; no secrets in step output. |
| T-70-03 | Spoofing | DataResult / Keeper* messages serialized without auth fields | accept | Internal RabbitMQ; contracts add no auth/secret surface; identical posture to existing Step*/Keeper* contracts. |
</threat_model>
