Research's live-verified label list for `http_server_request_duration_seconds_*` is http_route, http_request_method, http_response_status_code, url_scheme, network_protocol_version and otel_scope_name, and only the three `http_`-prefixed entries collide. Helper functions above the linear body, each with a block comment naming the mechanism: `Get-DashboardTargets` (walk panels[] and panels[].panels[] for nested rows, return objects carrying file, panel title, panel type, refId and expr), `Get-MetricTokens` (specified in full below — its position scoping is the load-bearing part), and `Add-Failure` (accumulate file + panel title + expr + remediation instead of throwing on the first error, so one run reports every problem).

`Get-MetricTokens` — POSITION-SCOPED. The metric family regex alone (`process_runtime_dotnet_\w+`, `orchestrator_\w+`, `keeper_\w+`, `processor_\w+`, `http_\w+`, `kestrel_\w+`, `messaging_\w+`, `dotnet_\w+`) also matches PromQL *label* names, which are not metric names and are not — and must not be — allowlisted. Plan 87-04's WebApi row makes this concrete and unavoidable: Panel 10 writes `sum by (http_route) (...)`, Panel 11 `sum by (le, http_route) (...)`, Panel 12 `sum by (http_response_status_code) (...)` and Panel 13 the in-selector `http_response_status_code=~"5.."` — all four match `http_\w+`, none is a metric. These are not invented forms; they are copied verbatim from the live-verified PromQL in 87-RESEARCH.md § "WebApi row (BPD-03)". An unscoped sweep therefore fails rule S9 on four correct panels, so the function MUST distinguish metric-selector position from label position.

Implement the position test as: a family-regex match is a METRIC token only when the next character after the match — allowing intervening spaces — is `{`. This anchor is complete for these two dashboards, because rule S7 / VAR-03 already makes `{source=~"$source", service_instance_id=~"$pod"}` mandatory on every metric reference, so every metric is written `name{...}`. And no label position can satisfy it: a label inside `by (...)`, `without (...)`, `on (...)`, `ignoring (...)`, `group_left(...)` or `group_right(...)` is followed by `,` or `)`, and a label inside a selector is followed by `=`, `!=`, `=~` or `!~`.

Do NOT implement the scoping instead as "strip the contents of the `by (...)` / `without (...)` / `on (...)` / `group_left(...)` clauses before running the family regex". That variant handles Panels 10, 11 and 12 but NOT Panel 13, whose colliding `http_response_status_code` sits inside the selector braces rather than in a grouping clause, and it would also miss the same collision anywhere it appears as a filter label. The `{`-anchor handles every case in both dashboards; the strip-clauses form does not.

Return the two sets separately, because the residue is itself load-bearing:
  - `Metric` — family-regex matches in metric-selector position (followed by `{`). Rules S9 and S10 test this set against the allowlists.
  - `Bare`   — family-regex matches NOT in metric-selector position. Rule S15 tests this set against KNOWN_LABELS, so the `{`-anchor cannot silently swallow a real metric that was written without its selector.

Wherever a rule below says "metric tokens" (C2, C3, C5, C7) it means the `Metric` set.
