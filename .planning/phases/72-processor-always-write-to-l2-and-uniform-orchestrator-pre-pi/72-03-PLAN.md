## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| inbound result → metric label | The `workflowId` tag value comes from the inbound message's `WorkflowId` |
| orchestrator → Redis (L2 read/delete) | The `out:` blob read/delete now runs for every outcome; a fault must escalate, a clean-absent must not |
| orchestrator → result-post queue | NextStepHandoff carries `Data` (the relocated blob) + `ExecutionId` downstream |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-72-07 | Denial of Service | `orchestrator_step_unresolved` label cardinality | accept | Single label `workflowId` (bounded authored-workflow Guid set), no free-text/`reason`/`stage` label (label-minimal by spec). Increment volume bounded by L1-resolution-miss frequency. |
| T-72-08 | Denial of Service | stage-3 dangling-id loop | mitigate | The loop iterates `selection.UnresolvedIds` (bounded by a step's declared `NextStepIds`); it `continue`s (graceful, never throws), preserving T-24-06 no-throw — a malformed workflow graph cannot wedge the consumer or trigger redelivery storms. |
| T-72-09 | Tampering / Repudiation | clean-absent mistaken for fault (or vice-versa) | mitigate | The read distinguishes clean-absent (`IsNullOrEmpty` → idempotent ack-skip, NO keeper) from a thrown `RedisException` (loop-exhaust → REINJECT). A clean-absent never escalates to the keeper (D-10), preventing spurious REINJECT amplification; a real fault still escalates, preventing silent loss. Proven by the clean-absent + ReadFault facts. |
| T-72-10 | Information Disclosure | trip-end / dangling-id logs | mitigate | All new logs (clean-absent, dangling-id) reference ids only (WorkflowId/StepId/NextStepId) — never the relocated blob Data or author payload (T-70-10), consistent with the existing trip-end logs. |
