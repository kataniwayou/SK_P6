<objective>
Build the orchestrator-side two-consumer Pre/Post core: a shared `OrchestratorPrePipeline` (gate/read
`L2[out:entryId]` -> `SelectNext` -> fan out one `NextStepHandoff` per match -> delete `L2[out:entryId]`,
with the D-18 two-reason trip-end on no-match/L1-miss), a shared `RelocateTail` (write `L2[data:messageId]`
on the Completed path then dispatch `EntryStepDispatch` with `entryId = messageId`), a new
`OrchestratorPostProcessConsumer` on the `orchestrator-result-post` queue, the `TypedResultConsumer` reshape
into a thin Pre shell, the `OrchestratorMetrics` trip-end counter, the TTL-floor options, the `Program.cs`
wiring, and the full test migration (new Pre/Post facts + flipping `TypedResultConsumerFacts`/`ResultAckTests`
from the L1-only straight-through model to the two-consumer + relocation model, asserting `executionId`
equality not regeneration).

Purpose: this is the heart of the phase — the symmetric mirror of Phase 70's processor pipeline applied to
the orchestrator (reads `out:`, writes `data:` — the inverse cross-pairing). No-silent-loss becomes
falsifiable via the trip-end metric (REQ-71-02). Output: 8 source files + 5 test files, full orchestrator
slice green.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| processor -> orchestrator (orchestrator-result queue) | Step-results carry `EntryId` (now the real out: blob key via A1) the Pre gates `L2[out:entryId]` on |
| orchestrator Pre -> orchestrator Post (orchestrator-result-post) | `NextStepHandoff` carries `Data` (relocated input JSON) + `Payload` across the broker (at-least-once, no dedup) |
| orchestrator Post -> processor (queue:{processorId:D}) | `EntryStepDispatch` with `entryId = messageId` directs the next processor to read `L2[data:messageId]` |
| orchestrator -> Redis (L2) | reads/deletes `out:`, writes `data:` — key operands derive from `EntryId` (inbound) and the fresh envelope `MessageId` (MassTransit-assigned) |
