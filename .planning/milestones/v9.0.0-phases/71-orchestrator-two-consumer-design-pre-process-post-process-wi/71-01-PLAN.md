<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| processor/keeper -> bus envelope | Step-result records cross the broker; the A1 stamp now puts a real `messageId` (the output blob key) into `EntryId`, a value other consumers gate on |
| contract serialization -> Redis key derivation | `OrchestratorInject.MessageId` / `OrchestratorReinject.EntryId` become L2 key operands downstream (plans 02/03) — a forged value could target another lineage's blob |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-71-01 | Tampering | A1 stamp (`EntryId = dr.MessageId`) | accept | `dr.MessageId` is the MassTransit-assigned envelope id the processor itself carried, not attacker input; the change only swaps a placeholder for the real key. No new external surface (internal bus, Phase-70 posture). |
| T-71-02 | Information Disclosure | new contracts carrying `Data`/`Payload` (`NextStepHandoff.Data`, `OrchestratorInject.Handoff.Data`) | mitigate | Contracts are data carriers only this plan; the never-log-payload discipline (T-70-10) is enforced at the CONSUMER log sites in plans 02/03. This plan adds no log statement that emits `Data`/`Payload`. Acceptance check: no new `Log*` call referencing `.Data`/`.Payload`. |
| T-71-03 | Spoofing | `messageId` in-body on keeper contracts (D-03 override) | accept | Mirrors the shipped Phase-70 keeper override (`KeeperReinject.MessageId`); the envelope-id override is the documented recovery mechanism, not a spoofing vector — no inbox/dedup is claimed on these endpoints (at-least-once posture, duplicates tolerated). |
</threat_model>
