<objective>
Complete D2 (LOG-02) and the keeper half of D1 (LOG-01). The keeper recovery consumers currently open NO ambient execution scope (the bus-wide `InboundExecutionScopeConsumeFilter` no-ops on them because keeper records were not `IExecutionCorrelated`), so today they hand-carry `{CorrelationId} {ExecutionId} {EntryId}` in the reinject log strings. Now that Plan 05 provides the loose-id `ExecutionLogScope.BuildState` overload AND made the keeper records `ICorrelated`, wrap each reinject consume in `logger.BeginScope(ExecutionLogScope.BuildState(...))` so Tier-1 arrives from scope, then strip the Tier-1 placeholders from the REINJECT sent/drop templates — keeping the Tier-2 `{MessageId}` (the one id the scope does not carry) and the Tier-3 `{ReinjectOutcome}` discriminator (D6/LOG-06). Make the processor-side and orchestrator-side consumers symmetric.

Purpose: the keeper's records look like every other framework record — Tier-1 from scope, `{MessageId}` on send/consume, domain extra otherwise.
Output: both reinject consumers scope-wrapped and stripped; the keeper fact suites updated (explicit state now carries only MessageId+ReinjectOutcome; a new scope-carrying fact proves the 5 ids arrive via BeginScope).

PHASE-78 HANDOFF (documented, do NOT fix here): once the keeper opens the scope, its reinject records gain `attributes.StepId` (and keep `{MessageId}` in the string), so they enter the analyzer's structural query and can look like processor "did-run" records. The live analyzer must discriminate them via `attributes.ReinjectOutcome` (only keeper records carry it) — that is Phase 78.
</objective>
