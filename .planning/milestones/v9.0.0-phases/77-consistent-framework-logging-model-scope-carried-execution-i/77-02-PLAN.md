<objective>
Capture and log the OUTBOUND envelope MessageId on the processor's result send (D3 / LOG-03 — the meatiest change). Today `OutputTail.SendResult` emits the Step* result via the plain `ep.Send((object)result, …)` overload with NO outbound-id capture and NO log, so the delivery-unit id minted for that send is invisible in the evidence picture. The three-tier model puts `{MessageId}` — the one id the ambient scope does not carry — in the string of every send/consume framework record. Mint the outbound id ourselves (the established `ctx => ctx.MessageId = …` idiom from `BaseProcessor.cs:102`), stamp it on the envelope, and log `"result sent {MessageId} {Outcome}"`.

Purpose: the send side of the round trip now carries its delivery-unit id, symmetric with the consume side's `hop executed {MessageId}`.
Output: `OutputTail.SendResult` returns the minted outbound id; `OutputTail.RunAsync` emits a FW-04-guarded `result sent {MessageId} {Outcome}` record; a new hermetic fact proves the logged id equals the stamped envelope id.

DESIGN CONSTRAINT (why an optional logger): `OutputTail` currently takes no `ILogger`, and EIGHT test files construct it directly via `new OutputTail(redis, context, send, …)`. Add the logger as a trailing OPTIONAL param defaulting to `null` (→ `NullLogger`), so every existing `new OutputTail(...)` call still compiles unchanged and production DI (`AddScoped<OutputTail>()`) fills the real logger. Do NOT change the `RunAsync` tuple shape (that would ripple into ProcessorPipeline and PostProcessConsumer, owned elsewhere).

PHASE-78 HANDOFF (documented): this adds a NEW framework send record. The live analyzer may now key produced-edges on the result-send `{MessageId}`; wiring that in is Phase 78.
</objective>
