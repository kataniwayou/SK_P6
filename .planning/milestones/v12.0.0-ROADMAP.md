# Milestone v12.0.0: Resilience & Health-Probe Hardening

**Status:** ✅ SHIPPED 2026-07-27
**Phases:** 86 (single phase)
**Total Plans:** 9

## Overview

Make every service tolerate infrastructure outages without crash-looping. A live experiment (v11.0.0-era) proved keeper + processor **crash-loop** under an unreachable RabbitMQ because their self-watchdog was tagged `"live"` — an infra fault tripped *liveness* (restart) instead of only *readiness*. This milestone corrected the category error: `/health/live` answers only "is my watchdog loop still turning?" (restart is the sole remedy for a silently-dead loop); `/health/ready` answers "are my required infra deps reachable + am I bootstrapped?" (NotReady, never restart); and recovery from a sustained outage is by **operator restart, not self-heal** (a hard readiness latch). One shared `BaseConsole.Core` primitive replaced the two divergent per-service watchdogs (orchestrator stays self-only — no beatable loop). The WebApi keeps its own `BaseApi.Core` pattern (Postgres + Redis latched; bus soft/Degraded).

Source of truth: the approved design spec `docs/superpowers/specs/2026-07-26-console-health-liveness-refactor-design.md`.

## Phases

### Phase 86: Console & WebApi Health/Liveness Refactor

**Goal**: Console (orchestrator/keeper/processor) and WebApi health probes refactored so an infrastructure outage (Postgres/Redis/RabbitMQ) never crashes the process nor restarts the pod — only a genuinely stalled watchdog loop restarts. `/health/live` checks only watchdog-loop liveness via one shared `BaseConsole.Core` primitive (`ILivenessHeartbeat` + `LoopLivenessHealthCheck`, k=3, opt-in — keeper + processor beat at the top of their loop before any infra I/O; orchestrator self-only); the two divergent per-service watchdogs retired. `/health/ready` reflects each service's REQUIRED infra deps plus, for the processor, identity+schema resolution — NotReady but never restart, with Redis newly included and the baseapi bus capped at Degraded (soft). "No self-heal" enforced by a hard readiness latch. A `startupProbe → /health/startup` added to all four k8s deployments.

**Success criteria (all TRUE):**

1. `/health/live` returns healthy iff the watchdog loop beat within `k × interval` (k=3); a stalled/dead loop goes stale → restart; an infra outage does NOT trip `/health/live`. (HLTH-01)
2. A Postgres/Redis/RabbitMQ outage never crashes the process nor restarts the pod: the fault is caught + logged on every loop — including `ProcessorStartupOrchestrator`'s identity/schema loop — and a live broker outage leaves all four services at `RESTARTS 0`. (HLTH-02)
3. One shared `BaseConsole.Core` primitive, opt-in; keeper + processor beat at the top of their loop before any infra I/O; orchestrator self-only; `KeeperLivenessWatchdogHealthCheck` + `BaseProcessor LivenessWatchdogHealthCheck` retired; processor beats unconditionally (Healthy gate only on the L2 write). (HLTH-03, HLTH-06)
4. `/health/ready` = each service's required infra deps plus, for the processor, identity+schema resolved; NotReady never restarts; Redis included; baseapi bus capped at Degraded, NOT latched. (HLTH-04, HLTH-08)
5. No self-heal: once a required dep fails for its readiness `failureThreshold` window, `/health/ready` latches Unhealthy until process restart; migration stays one-shot. (HLTH-05)
6. Startup-gate marking per service (orchestrator=hydration, keeper/processor=first beat, baseapi=migrations) and a `startupProbe → /health/startup` on all four k8s deployments. (HLTH-07)
7. Live proof: the broker-unreachable experiment — all four services stay running (`RESTARTS 0`), go NotReady, show caught+logged errors; recovery only on restart. [verification gate]

## Milestone Summary

**Verification:** Phase-86 goal verification **8/8 must-haves PASSED** (verifier independently re-read source, confirmed retired watchdog files deleted + startupProbes present, re-ran hermetic). Full hermetic suite: **zero Phase-86 failures** (the ~23-24 residual failures are all pre-existing/environmental — 18 dead `ComposeYamlFacts` for a `compose.yaml` deleted in the k8s-only refactor + ~5-6 live-infra tests). Both Debug + Release builds 0-warning.

**Live proof (twice):** the broker-unreachable experiment on Docker-Desktop k8s (deployed under unique tags to defeat the `:local` stale-image trap): all four services stayed **`RESTARTS 0`** over 4+ minutes, went NotReady (`/health/live` 200, `/health/ready` 503), logged caught `BrokerUnreachableException`, and recovered only on restart. Re-run against the code-review-fixed bits (tag `p86fix-8af3adc`) — same result, and CR-01's sanitized readiness message confirmed live.

**Code review:** 10 findings. **CR-01 (Critical)** — `/health/ready` could leak inner driver exception detail before the latch trips — fixed (both latch mirrors return a static message on every Unhealthy path). WR-01 (probe bound), WR-02 (config-derived interval), WR-03/04/06 (docs), IN-01/03 fixed. **WR-05 applied-then-reverted**: bounding the first-time multiplexer resolution into the ping budget regressed a reachable-but-cold Redis to false NotReady (caught in post-fix verification, reverted).

**Key decisions:**
- Retired the two divergent per-service watchdogs for one shared `BaseConsole.Core` opt-in primitive; beat unconditionally at the top of the loop, above infra I/O and above the Healthy gate.
- Hard readiness latch (no self-heal) for required deps; baseapi bus stays soft/Degraded (publish-relationship, not a required dep).
- k8s startupProbes added to all four with a ~150s grace window covering rabbitmq cold start.

**Known tech debt / follow-ups (advisory, non-blocking):** WR-05's underlying theoretical concern (first-time multiplexer resolution off the bounded window) accepted as won't-fix. Pre-existing: 18 dead `ComposeYamlFacts`, ~5-6 mis-tagged live-infra tests.
